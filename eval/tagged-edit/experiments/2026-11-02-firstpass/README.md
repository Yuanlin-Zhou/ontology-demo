## 诊断口径与遗漏

- **中断恢复的 3 条误报：**三组 stop 都用本地标志记录 while 重试中的中断，终止后恢复标志。InterruptProbe 验证调用线程预先中断、实际任务仍阻塞、正常排空后标志恢复，3/3 通过；原 TP-SHUTDOWN-003 诊断保留，不据此重写静态分数。
- **局部 catch 与任务拒绝传播政策：**原 TP-REJECT-003 要求提交处捕获和补偿；QUEUE / ASYNC 任务明确要求让调用方收到 RejectedExecutionException。不能把这些命中一概当作真实业务缺陷，也不能擅自删除组织规则。CONTEXT 保留了原有提交策略。此处是需要明确的任务 / 规范政策边界。
- **继承的问题：**CONTEXT 的默认拒绝策略等诊断在初始代码中就存在。原始文件级遵循率包含预存与新引入问题，不直接等于修改质量。
- **异常记录漏检：**Baseline / RAG 的空 catch 没有触发 TP-SUBMIT-005，但本轮明确要求失败记录；实际 LoggingProbe 失败。它是校验器覆盖缺口，不能靠一个 passed 状态证明全部规则语义满足。本轮不修改 checker 或重跑模型来改变结果。
- **标签组的额外命名提醒：**tagged 新增的线程池没有显式 ThreadFactory，出现额外 TP-CREATE-003 warning。显式 planned 只覆盖队列、拒绝、异常、关闭，未包含命名分支，说明“新能力计划”的知识覆盖仍有缺口。

change-local-audit.json 单独比较同一冻结实现下的输入和输出：三组均解决无界队列 TP-CONFIG-004、上下文 TP-SUBMIT-004；新建池会引入原来没有的适用规范。该比较只是描述性变化，不是独立准确率基准。

## 补充验证与边界

15 项独立 JVM 诊断均符合预期：9 个现有调用方编译通过；3 个中断恢复场景通过；3 个日志场景中两组复现失败、一组通过。这里不能把“符合失败预期”写成业务验收全通过。postrun-probes.json 保留实际状态及诊断，探针只改自己的测试源码，不改模型 Java。

三个试点、每组只生成一次，且任务与验收由开发过程编写，并非独立保留集。任务已明确单 worker、队列容量等参数，本轮也 **不能验证知识树是否帮助正确决策线程数 / 队列选型**。尚未验证跨文件接口实现关系、自动计划新能力、独立人工标签准确性。旧平铺规则实验与本轮不混算。

源码静态检查仍只覆盖有限模式；本轮 stop 的长期等待、不可中断任务等完整生产关闭语义没有被宣告通过。任务范围内审查不能代替这些要求。

## 下一步建议

先由领域开发者独立审阅知识叶子、标签和任务边界，加入未用于开发的真实修改需求，明确拒绝传播政策与新能力的必要知识；再冻结新的验收。参数决策任务应提供负载与资源约束，允许合理的多种实现，不直接把所有答案写进任务。继续保留首次修改、预算、原始分数及单独诊断，不自动扩大调用或追加修复。
