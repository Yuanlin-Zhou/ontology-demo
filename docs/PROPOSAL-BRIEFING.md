# 创新提案阶段汇报：基于分层知识与代码实体标签的 Agent 精准知识召回

汇报日期：2026-11-02。以下按 7 页 PPT 组织，附口头稿与问答。内容已按原始目标修订：风险诊断是验证组件，不再把项目目标改成检查工具。

## 一句话结论

目标是把现有知识库组织为分层知识树，将类、接口、方法与最小知识分支关联，在 Agent 修改代码时局部召回相关知识，验证规范遵循是否改善。目前已完成前期规则引擎与生成实验，并补齐分层知识、轻量实体标签图和修改实验准备；完整路线尚未开展新的付费模型效果验证。

## 第 1 页：业务问题与原始目标

企业规范存在于文档里，但 Agent 修改局部代码时，不一定能获取真正相关的知识。全量注入文档会占用上下文，普通片段检索也未必体现工程上的适用条件。

本提案分三步：

1. 将知识组织成类似思维导图的层级，区分创建参数的决策知识与使用代码的规范。
2. 给代码实体关联最小知识分支，保存标签依据及知识来源。
3. 每次修改时按涉及实体与新增能力计划召回少量知识，比较 Agent 是否更符合规范。

预期价值是减少规范遗漏和无关知识干扰，形成可追溯知识资产。当前没有已验证的研发工时节省、生产事故下降或货币收益数据。

## 第 2 页：方案流程与创新点

```text
知识文档 → 分层知识树 → 最小决策 / 规范叶子
                             ↕ 关联
现有代码 → 类、接口、方法、字段 → 轻量 CodeGraph 标签与证据
                                      ↓
本次修改实体 + 明确新增能力 → 局部知识召回 → Agent 修改代码
                                                   ↓
                                      规范校验 + 编译 + 行为与任务验收
```

区别在于把“知识层次—代码实体—修改范围”连接起来，再用实际修改结果验证收益。不是宣称首创图谱、静态分析或 RAG，也不替代编译器与测试。

## 第 4 页：前期简化路线的实验发现

第一轮重点实验：21 任务 × 无知识 / BM25 RAG / flat Rules，共 63 次首次生成。deepseek-flash、相同任务与初始代码、temperature=0、知识预算均为 1200 估算 tokens，无 Repair。

| 指标 | Baseline | BM25 RAG | flat Rules |
| --- | --- | --- | --- |
| 平均静态规范遵循率 | 82.2% | 85.6% | 90.9% |
| 编译通过 | 21/21 | 20/21 | 21/21 |
| 已配置行为测试通过 | 18/21 | 18/21 | 19/21 |
| 实际总 token | 27,556 | 44,615 | 46,264 |

规则组遵循率高 8.7 个百分点，行为多通过 1 例，但 tokens 高约 67.9%。静态遵循按 20 个有适用规则的样本计算，诊断中存在误报；不能解释为完整业务成功率或普遍收益。

这些实验使用单文件特征匹配平铺规则，尚未验证“分层知识 + 持久实体标签 + 修改时局部召回”的完整方案。不能把前期结果直接作为完整方案成功或失败的结论。

## 第 5 页：严格验收带来的经验

后续 9 任务 × 3 策略实验明确了更严格的业务约定：Baseline / RAG / flat Rules 的业务验收通过为 2/9、3/9、3/9，编译为 9/9、9/9、8/9；tokens 为 17,561、25,401、26,707。

进一步审查确认，8 份自动通过代码仍在强制关闭时丢弃已接受任务。结合原先 19 个门控失败，按本轮完整明确契约，三组均为 0/9。这表示每份代码至少有一项必需约定未满足，不表示所有基本功能都失效。

由此得到三点经验：

- 规范遵循、编译通过、行为通过和完整任务完成必须分开统计。
- 仅凭代码中出现规范要求的结构，不能证明实际业务行为正确。
- 必须保留原始结果、用独立验收识别误报漏报，不能通过改标准制造收益。

已对 90 份历史输出完成零模型调用复盘，并修复局部检查缺口。检查能力服务于原始研究目标，不取代原始目标。

## 第 6 页：当前修改实验如何验证原目标

三份初始代码均完整可编译，执行相同修改：

| 任务 | 修改内容 | 验证重点 |
| --- | --- | --- |
| 队列改写 | 无界通知缓冲改为两项有界缓冲 | 实际排队容量、过载拒绝、业务回调和关闭排空 |
| 新增异步 | 同步事件发布改为有界实例线程池 | 旧标签没有新能力时的 planned 知识补足、实际异步执行 |

该三组对比考察完整方案，包括知识整理和召回方式；如需隔离“标签选择算法”的贡献，还应另外比较相同叶子语料上的不同检索方式。开发试点也不能替代独立保留集。

## 第 7 页：后续建议与需要确认的事项

建议沿原目标继续，以一个有边界的验证周期为单位，不立即做 Cline 自动改写集成：

1. 由熟悉线程池的开发者审阅知识树，确认层级、最小分支和决策条件。
2. 审阅实体标签、局部召回与更新机制，补充独立的应召回 / 不应召回标注。
3. 冻结未参与开发的实际修改任务与验收，再确定模型调用预算，执行完整路线的三组对比。
4. 若规范遵循、功能保持、误报漏报与维护成本均可接受，再将召回能力接入 Agent，先显式调用并保留追溯。

需要确认：一个实际代码场景、领域开发者参与评审，以及后续验证的时间 / 人力 / 模型调用上限。具体继续或停止标准在实验前确定。目前没有获批预算或已量化的工时节省承诺。

## 约 3 分钟口头汇报稿

这个提案的原始目标，是让 Agent 修改代码时获取少量真正相关的企业知识。我们计划先把知识库组织为层级，再将类、接口和方法与最小知识分支关联，最后按本次修改范围召回知识，观察是否能写出更符合规范的代码。

前期我们先做了简化的规则引擎，用 Java 线程池领域验证语义分析、规范召回与生成后校验。已有 26 条规则和 21 个基础用例。较完整的一轮实验中，规则组静态规范遵循率为 90.9%，Baseline 为 82.2%，行为测试多通过一例，但 token 用量增加约 68%。更严格验收又发现共同的业务边界缺陷，所以还不能证明整体收益。

这些结果验证的是前期平铺规则路线，并不等于验证了完整的原始方案。因此我们保留原目标，继续补齐知识分层和实体标签，而不是把目标改成静态检查工具。

目前已经补出了两条知识主干和 15 个最小叶子，区分决策知识与编码规范；代码实体标签保存证据和来源，轻量图记录字段引用与本地调用，修改时只沿有限关联召回。代码或知识变化后，旧图不能继续使用。新增能力还可通过明确的计划补充，避免现有标签覆盖不到新功能。

同时准备了三个完整代码修改任务，比较不注入知识、普通文档 RAG 和按实体标签召回。行为验收关注真实队列容量、异步回调、关闭与租户上下文。目前没有新增模型调用，也没有新的效果成绩。

下一步建议先请领域开发者确认知识层级和标签，再用独立实际修改任务冻结验收与预算，验证完整路线。只有效果和维护成本都能接受，再考虑接入 Agent。希望先确认一个实际场景及评审支持，并约定投入上限。

## 可能追问及回答

**与普通 RAG 的区别是什么？** 当前 RAG 对照按关键词检索文档片段；新路线按代码实体关联的知识分支召回，并区分已有事实与计划新增能力。不宣称优于所有高级 RAG。

**与静态扫描有什么区别？** 静态扫描和本项目 checker 用于测量及反馈；提案的核心是生成前的知识组织与局部召回。成熟扫描能力应尽量复用，不重复制造编译器。

**为什么不直接使用大型 CodeGraph？** 初期用 JSON 验证实体、标签、边与失效机制，避免先投入图平台建设。当前文件内关系足够验证最小闭环，跨文件语义仍未完成。

**知识是否自动生成、接口是否自动打标？** 当前知识人工整理；可见实现按 AST 打标。抽象接口没有实现证据时不猜测并发语义，可带理由人工关联。自动知识抽取和跨文件实现传播尚未验证。

**现在是否已经证明有效？** 尚未。前期实验有方向性观察，但完整标签路线当前只有本地验证和准备产物，没有新的模型对比结果。
