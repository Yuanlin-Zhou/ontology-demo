1. **强制关闭丢任务：已有诊断，不是完全漏检。** 2026-11-02 独立 JVM 探针确认的 8 份自动通过代码，在修复前就全部收到 TP-SHUTDOWN-004 warning。之前的自动业务验收只覆盖正常排空，且 error 门控不阻止 warning，所以“业务验收通过”与“存在关闭风险警告”同时发生。这首先是验收覆盖及门控策略的问题，不能宣传成本次新增检测能力。
2. **调用者上下文泄漏：已有 error。** 两轮中已确认泄漏的 Baseline / Rules（旧轮）和 Baseline / RAG（新轮），4 份都已被 TP-SUBMIT-004 检出，证据关联到未被 finally 保护的 validateTenant 调用。无需为这些原始样本制造新的修复效果。
3. **取消后队列未释放：确有检查器缺口。** TP-SUBMIT-002 的知识正文已有实际执行句柄和队列身份要求，但检查器原来只检查 get 是否有超时，没有检查 execute 包装器与 remove 对象是否一致。业务测试和源码审查已经发现，而静态诊断没有指出。

## 本次实现与证据

- `src/validator/checks/cancellation.ts`：有限的同方法执行边界内入队身份检查。直接任务可通过 remove(task) / purge 清理，lambda 包装器须移除包装器。其他线程、其他池、条件分支或延迟 lambda 中的 remove 不被当作当前取消路径已清理。检查随 TP-SUBMIT-002 执行；默认适用条件仍是已有 Future 等待特征，不覆盖所有 cancel 使用。
- `src/validator/checks/context-cleanup.ts`：32 状态阈值的有界显式路径分析、一层私有 helper，支持 remove、稳定旧值恢复和相应 finally。循环、复杂控制流、跨文件与隐式异常顺序不作完整证明。
- TP-SHUTDOWN-004：直接丢弃之外，增加未读取局部任务列表的识别；不把日志数量、转交未知方法等同于任务完成。
- `tests/rule-coverage.test.ts`：旧生成代码回归、正反例及边界；真实 JVM 对照直接恢复、延迟清理、条件清理后的线程上下文。JVM 场景中不安全写法的探针通过，表示“成功复现泄漏”，不是业务验收通过。

在修复前提交 53a46ea 的隔离源码副本上运行了相同的 9 个命名例子，证实 5 个漏报例子和 1 个误报例子，另 3 个正例保持不报。它们是为已知缺陷构造的回归例子，不能据此报告总体精确率或召回率。原始输入及逐例诊断见 `fixture-comparison.json`、`fixtures/`。

90 份源码修复前后静态重查，新增诊断集中于两轮 CASE-020 的 6 份输出，共 12 条 TP-SUBMIT-002 warning；其他规则的诊断位置集合不变。旧轮 RAG CASE-020 本身不能编译，新增诊断仅代表源码模式风险，不能称为该代码已执行出的业务缺陷。新轮 Rules 的实际容量滞留已有原始行为测试证据。

## 核心价值和接入决定

工具当前的核心价值是：**将适用的研发规范及文件内可定位的风险证据交给开发者或 Agent 审阅**。适合标准线程池 API 误用和局部资源 / 上下文模式检查；不承担编译器、完整控制流证明、分布式可靠性或完整业务验收。

现在不直接接入 Cline 自动修改或自动通过门控。CLI 和 API 已可用于手动召回 / 校验；下一步若决定接入，只提供显式调用的 retrieve / validate 诊断展示：同时显示源码证据、规则来源、severity、语法 / unavailable 状态，以及省略规则，不把 passed / complete 文案等同业务正确。由用户或 Agent 判断如何修改，修改后仍运行编译和相关测试。

接入前还缺跨方法取消与复杂关闭路径的独立标注覆盖；当前 90 份开发样本和定向回归不足以宣称检查能力整体可靠。因此本轮完成能力收敛和缺口修复，保留集验证后再决定 Cline 适配，不新增付费生成，也不实施自动 Repair 集成。

所有 26 条规范的可检查范围与人工边界见 [能力清单](CAPABILITIES.md)。
