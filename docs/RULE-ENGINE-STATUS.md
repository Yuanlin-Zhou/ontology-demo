## 剩余问题到底在哪里

Rules 三份业务失败都是生成代码的真实问题：

- 优先级淘汰：遍历排序队列时不断覆盖候选，最终选中最低优先级中最新的任务，而非最旧任务。
- 虚拟线程关闭：重复 stop 因 CAS 失败直接返回，未等待已接受任务结束。
- 导出取消：取消 FutureTask 但未从队列移除，取消任务继续占用容量。

这三项失败保持原状；没有通过改业务验收、改模型源码或再调用模型消除。

6 条 error 诊断也不能直接当作 6 个真实违规。核查后，4 条是真实规范违规实例：优先级服务未等待关闭；报价服务使用快捷工厂、无界队列且没有关闭路径。另两条是引擎误报：

1. 重试服务两个构造器都经同一工厂初始化 final 字段，引擎无法将关闭调用关联回创建节点。
2. 虚拟线程服务通过局部标志在 finally 中恢复中断，引擎只看 catch 体，错误报告未恢复中断。该服务仍有独立、真实的重复关闭缺陷。

## 本轮实际修复的引擎缺陷

实验结束后，仅修改核心资源解析和回归测试，未修改任何 case：final 字段在多个替代构造器中的赋值，若全部立即发生于构造器、且都解析到同一个创建节点，现在关联为同一资源。不同工厂、普通方法重新赋值、延迟 lambda 赋值仍不合并。

现有同一批模型源码零调用重查，三个策略各少一条资源关联误报，error 诊断变为 24 / 23 / 5。该复查单独保存，原始表格仍是冻结版本的 25 / 24 / 6。当时 finally 标志恢复中断的误报尚未修复，5 条不能全称作真实违规；后续修复见下节记录。

核心流水线与数据集回归 47/47 通过、0 跳过；TypeScript 类型检查、git diff --check 通过。修复的是资源身份解析，不是让样例迁就校验器。

之前已经修过的关键引擎问题包括：错误的 Thread/Future API 建议；同名变量与多池资源串用；完整提示词知识预算；校验未完成却显示无违规；编译/业务门控与有限修复。具体实现及边界见 ENGINE-REVIEW.md。这些组件修正并不自动证明生成策略有效，以上冻结对比才是本轮的效果证据。
